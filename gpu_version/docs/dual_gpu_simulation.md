# Dual-GPU simulation in SPHExampleGPU

Running two independent cases, one on each GPU, can increase throughput immediately. Advancing one case across both GPUs requires a new solver path. A spatial split is a practical design because each particle interacts with neighbors within a finite kernel support. The main benefits would be fitting larger cases and potentially reducing elapsed time for compute-heavy cases. Both benefits depend on the fraction of particles near the split, load balance, and the transfer path between the devices.

## Where the current solver would change

The ordinary GPU path uploads a single set of particle arrays and advances it with one cell-list workspace, one set of support arrays and one device timestep state. The interaction, integration and graph scheduling are tied together in `enqueue_step!` and `SimulationLoop`. The variable-resolution driver coordinates multiple particle pools through a shared device step. Its transfer logic handles changes of resolution, so it does not provide a cross-device transport. [Ordinary GPU driver](../src/SPHCellList.jl) · [Cell grid](../src/GPUCellGrid.jl) · [Variable-resolution driver](../src/GPUVariableResolutionDriver.jl)

| Solver concern | Proposed two-GPU design |
| --- | --- |
| Ownership | Split the domain at a shared cell face along a long axis. Each particle has one owner and a stable global ID. Each owner advances its particles and maintains read-only copies of its neighbor's particles near the interface. |
| Neighbor search | Build a local grid over owned and imported particles using a common cell origin, spacing and cutoff. Keep imported input fields dense and launch interactions only for owned targets. Same-device and cross-interface neighbors use the existing directed pair calculation. |
| Migration | At an accepted-step boundary, transfer any particle that crossed the split, including its identity and persistent model state. Keep ownership fixed during the predictor and corrector so results go back to the same particle. Rebuild or invalidate any reorder indices and predictor mappings that refer to old slots. |
| Time integration | Give both devices the same accepted time, timestep, output deadline and stop decision. Combine the existing local timestep criteria globally and apply the configured controller once. A rebuild or capacity error on either device must prevent a partial step commit. |
| Output | Gather owned particles from a single accepted time and merge by ID. Form the grid export from the union of occupied cells at that time, with the same cell origin and spacing on both sides. Reuse the existing writer after the merge. |

The first implementation should rebuild each stage's local neighbor ranges from the stage positions. With this design, a halo at least one maximum interaction radius wide, measured from the most advanced owned target at that stage, includes every eligible source. For example, if a predictor allows owned targets to move past the split by a distance `d`, the remote source selection must reach at least `H + d` from that split. Reusing old halo membership or cell bins between stages would require a conservative skin for target and source motion and a coordinated refresh trigger. Grid cell width is not the halo width. Changing cell subdivision leaves the physical interaction cutoff unchanged. [Cell grid](../src/GPUCellGrid.jl) · [Kernel definitions](../src/SPHKernels.jl)

## A first prototype

1. Start with ordinary symplectic stepping, a uniform resolution, fixed DBC walls and a static split. Disable CUDA graphs and predictor fusion in the first implementation so that each exchange has an explicit stage boundary. Begin with one CUDA.jl task per device, with device-local allocations and streams. Verify peer access on the actual GPU pair and measure both transfer directions. Use explicit copies of packed, persistent halo buffers, with reusable pinned host staging when peer copies are unavailable. [CUDA.jl multi-GPU documentation](https://cuda.juliagpu.org/dev/usage/multigpu/) · [NVIDIA multi-GPU programming guide](https://docs.nvidia.com/cuda/archive/13.4.3/cuda-programming-guide/03-advanced/multi-gpu-systems.html)
2. Exchange accepted positions, velocities, densities and source metadata before the first force evaluation. Advance owned predictors, exchange predictor state, then run the corrector. Derive pressure and inverse density from densities at the same stage on each device. Preserve pair orientation, viscosity, density diffusion, position precision and traversal settings in the single-GPU comparison. [GPU step and interaction setup](../src/SPHCellList.jl)
3. Once the synchronous version passes, overlap packing and transfer with interactions for owned targets whose entire support is local. Run interface targets after the incoming transfer completes. Count owned interaction candidates or measured stage time on each device to identify imbalance. Shift the cut by whole cells infrequently if the improvement justifies migration and rebuilding. Consider per-device graphs only after stage buffers have stable addresses and the exchange schedule is correct.

Actual mDBC adds a dependency at each stage where the selected scheme corrects the wall. A wall owner needs neighboring fluid state around the wall's ghost query position, which can extend beyond the ordinary halo for wall particles. Interface neighbors then need the corrected wall fields before the main force pass. Preserve stable compact boundary slots and ship any mode-specific corrected state that cannot be recovered from density alone, including Updated-mDBC wall pressure where applicable. A floating body spanning the split would additionally need owner-only contributions to a global force and torque reduction and one authoritative pose. Periodicity, open boundaries and variable resolution each need their own halo and ownership rules. [Boundary correction](../src/UpdatedMDBC.jl) · [Floating-body code](../src/GPUFloating.jl) · [Periodic search](../src/GPUPeriodicSearch.jl)

## Validation and expected scaling

Use [StillWedgeMDBC.jl](../example/StillWedgeMDBC.jl) as a small interface regression. Its default configuration selects `NoMDBC` and uses roughly 3,000 particles. Split through the wedge to exercise wall and fluid neighbors on both sides, then add a separate flow case with known migration across the split. For the supported mode, compare directed neighbor IDs, stage densities, force and density derivatives, timestep and rebuild behavior, and accepted state by particle ID. Check that every ID is owned exactly once, output has no duplicate IDs, fixed-wall state follows the single-device behavior, and particle and grid frames agree at the same sample times. Different accumulation order can produce floating-point differences, so use measured tolerances and compare physical observables over longer runs. Add an actual mDBC case before enabling that mode. [StillWedge walkthrough](StillWedgeGPUWalkthrough.md)

For an interface of area `A`, volume particle density `n` and halo width `w`, a uniform 3D estimate is `A × w × n` imported particles per device per exchange. In 2D use interface length and areal particle density. Multiplying by packed record bytes gives bytes transferred per direction. Symplectic stepping exchanges at least two states per step, with additional costs for migration and any corrected boundary data. Each stage pays for the slower device, exposed communication, and synchronization. Thin or badly imbalanced partitions increase this cost relative to useful work. Live memory per GPU includes owned particles, imported particles, grids, predictor and reorder buffers, and transfer storage. Allocator reservations and output staging need separate accounting.

After correctness passes, compare steady-state timings for a larger 3D case that fits on one GPU, then run a case whose particle state requires both devices. Report the two devices, link and peer-access mode, precision, particle and wall counts, halo bytes, migration counts, and owned and halo memory peaks. Warm kernels and graphs, alternate run order, and compare whole-solver elapsed times with matching physical duration, output settings, and recorded step, rebuild and readback counts. Report speedup separately from increased capacity. The small StillWedge case can validate correctness, but transfer latency and additional launches may dominate its runtime.
